# Child-Safe Rendering Finality — Implementation Reference

## Preventing Unauthorized Adult and Age-Restricted Content Rendering to Children Through Hardware-Rooted Execution Finality

**Source specification:** `draft-das-child-safe-rendering-finality-03`  
**Source date:** 31 August 2026  
**Author of source draft:** Sangam Das, Independent Inventor  
**Status of this file:** Engineering implementation reference derived from the source Internet-Draft.

> **Central protocol principle:** Permission to deliver content is not permission to render it.

This document translates the Internet-Draft into an implementation-oriented architecture for operating-system, confidential-computing, media-pipeline, GPU/compositor, display, audio, casting, mirroring, XR, browser, application, and device-security engineers.

It deliberately distinguishes:

- **requirements stated by the draft**;
- **reference implementation logic derived directly from those requirements**; and
- **deployment choices that the draft intentionally leaves open**.

It does **not** define a universal age-estimation algorithm, identity system, content-classification system, biometric system, transport, cryptographic algorithm, or vendor-specific GPU interface.

---

# 1. Security Property

The protected effect is **perceptibility**.

A restricted object can be:

- delivered;
- downloaded;
- cached;
- buffered;
- retained locally;
- generated by AI;
- decrypted inside a protected pipeline; or
- decoded into protected memory,

while still remaining **NON-RENDERABLE**.

The required transition is:

```text
RESTRICTED CONTENT
        |
        v
RESTRICTED CONTENT CANDIDATE ACT
        |
        v
NON-RENDERABLE
        |
        v
PROTECTED ENFORCEMENT DOMAIN (PED)
        |
        +-- recipient / eligibility
        +-- content / classification
        +-- device / application
        +-- policy / jurisdiction
        +-- policy epoch
        +-- revocation epoch
        +-- freshness / nonce
        +-- attestation
        +-- output target
        +-- intended Finality Sink
        |
        v
PROTECTED VALIDATION EVIDENCE
        |
        v
SCOPED NON-BEARER RENDERING FINALITY AUTHORITY
        |
        v
PROTECTED RENDERING FINALITY SINK
        |
     +--+--+
     |     |
   VALID  INVALID / ABSENT / STALE
     |     |
     v     v
 RENDER   KEEP NON-RENDERABLE
```

The Finality Sink is not merely a policy endpoint. It is the protected boundary at which a restricted object first becomes perceptible or can be trivially converted into a perceptible representation.

# 2. Non-Negotiable Invariants

An implementation conforming to the draft's security model should preserve these invariants.

## 2.1 Delivery is not rendering authority

```text
CONTENT DELIVERY != CONTENT RENDERING AUTHORITY
AGE CHECK        != DISPLAY FINALITY
CLASSIFICATION   != DECRYPTION AUTHORITY
SERVER ALLOW     != DEVICE-SIDE MATERIALIZATION AUTHORITY
```

## 2.2 Candidate Acts remain non-renderable during validation

The Candidate Act MUST remain non-renderable while required validation is incomplete.

## 2.3 Upstream age assurance is only an input

A successful age check MUST NOT itself cause decryption, decoding, display, audio, casting, mirroring, or another protected rendering effect.

## 2.4 Validation evidence precedes or is atomic with authority issuance

The PED commits protected validation evidence before, or atomically with, issuance of Rendering Finality Authority.

A Boolean `ALLOW` alone is not finality authority.

## 2.5 Authority is non-bearer in the architectural sense

Possession alone is insufficient. The Finality Sink independently verifies the protected bindings before enabling the requested effect.

## 2.6 Output effects do not silently widen

`DISPLAY` does not imply `CAST`.  
`DISPLAY` does not imply `MIRROR`.  
Authority for one device does not imply another device.  
Authority for one content digest does not imply modified content.

## 2.7 Failure is fail-closed

Missing, malformed, expired, stale, replayed, revoked, consumed, mismatched, or otherwise unverifiable authority leaves the restricted effect non-renderable.

No "warn and continue" path is permitted for protected content subject to this profile.

## 2.8 No alternate protected path may bypass the sink

If a deployment claims to protect a rendering path, ordinary application code must not be able to turn a denied Candidate Act into perceptible output through a different unprotected route.

# 3. Components

A practical implementation can be decomposed into the following components.

## 3.1 Policy / Evidence Adapters

Inputs may come from:

- privacy-preserving age verification;
- platform account state;
- parental-control systems;
- device age registration;
- content classifiers;
- regulatory policy;
- trusted identity providers;
- device policy;
- enterprise or family-safety services;
- device or sink attestation;
- protected user-presence mechanisms.

These systems establish facts or policy inputs. They do **not** directly complete the rendering effect.

## 3.2 Candidate Builder

Creates a `RestrictedContentCandidate` for each protected materialization attempt.

The Candidate Builder must capture the load-bearing content, recipient, policy, render, freshness, and sink context before protected rendering.

## 3.3 Protected Enforcement Domain (PED)

Evaluates all predicates required by the deployment.

The PED is the authorization decision point for creation of Rendering Finality Authority, not the final materialization point.

## 3.4 Protected Validation Evidence Store

Commits evidence before or atomically with authority issuance.

Possible mechanisms identified by the source draft include:

- protected signed record;
- MAC;
- enclave assertion;
- HSM assertion;
- sealed state;
- monotonic-state commitment;
- append-only protected record; or
- equivalent protected mechanism.

## 3.5 Rendering Finality Authority Issuer

Issues scoped authority only after successful PED evaluation and evidence commitment.

## 3.6 Finality Sink Verifier

Reconstructs or receives the Candidate Act and verifies the current authority immediately before materialization.

## 3.7 Materialization Adapter

Controls the actual protected effect, such as:

- content-key release;
- decryption;
- decoder enablement;
- GPU command submission;
- protected-surface creation;
- compositor admission;
- display enablement;
- audio output;
- XR compositor access;
- secure-video path;
- casting; or
- mirroring.

## 3.8 Epoch / Revocation / Replay Store

Maintains current:

- policy epoch;
- revocation epoch;
- authority-consumption state;
- nonce/replay state;
- protected session state;
- Temporary Under-18 state;
- device-registration baseline;
- security epoch where used.

# 7. RenderingFinalityAuthority

Required authority fields:

```text
authority_id
candidate_act_id
candidate_digest
validation_evidence_ref
permitted_effects
sink_id
policy_epoch
revocation_epoch
nonce
issued_at
expires_at
consumption
```

Additional binding fields defined by the schema include:

- content digest;
- recipient context ID;
- device ID;
- application ID;
- sink type;
- max frame count;
- max duration; and
- signature or MAC.

The source requirement is broader than the minimum JSON `required` array: Rendering Finality Authority must be appropriately bound to the act, content, recipient, device, application where applicable, policy epoch, revocation epoch, freshness, effect, and sink.

## 7.1 Consumption Modes

```text
SINGLE_USE
FRAME_WINDOW
SESSION_BOUND
```

### SINGLE_USE

Reference logic:

1. verify all bindings;
2. atomically verify that the authority/nonce is unused;
3. consume it before or atomically with effectuation;
4. reject every later presentation.

Suitable for one-shot high-risk consequences.

### FRAME_WINDOW

Reference logic:

1. verify authority at window creation;
2. bind the protected window to the authorized session/content/policy/sink;
3. track frame count where `max_frame_count` is present;
4. track duration where `max_duration_ms` is present;
5. stop rendering on the first exceeded bound or invalidating state change;
6. require new or renewed authority before rendering resumes.

This mode avoids cryptographic authorization on every frame.

### SESSION_BOUND

Reference logic:

1. bind authority to a protected session;
2. enforce its expiry and current epochs;
3. invalidate or revalidate on meaningful security transitions;
4. prevent transfer of the session to a different device/profile/application/output/sink unless specifically reauthorized.

# 8. Candidate Digest and Cryptographic Representation

The schema defines a `candidate_digest` with a SHA-256 textual form.

The source draft does **not** fully standardize:

- canonical serialization used to compute that digest;
- signature algorithm;
- MAC algorithm;
- key-discovery mechanism;
- certificate format;
- COSE/JWS encoding;
- exact proof-of-possession mechanism.

A GitHub reference implementation should therefore make these choices explicit and versioned.

**Do not silently hash arbitrary JSON serialization.**

Recommended engineering requirement:

```text
canonical_candidate_bytes(candidate, profile_version)
    -> deterministic bytes

candidate_digest =
    "sha256:" + HEX(SHA256(canonical_candidate_bytes))
```

The canonicalization method is a profile decision until standardized. Two implementations must not claim interoperability unless they produce identical digest input bytes for the same Candidate Act.

Likewise, `signature_or_mac` should be implemented through a pluggable protected authenticator interface rather than treating the placeholder string as a security mechanism.

# 9. PED Evaluation Algorithm

The following is implementation pseudocode derived from the draft's required predicates.

```text
function evaluate(candidate, protected_device_state, current_state):

    validate_schema_strict(candidate)
    require(candidate.version == "1.0")
    require(now >= candidate.freshness.created_at)
    require(now < candidate.freshness.expires_at)
    require(nonce_is_fresh(candidate.freshness.nonce))

    # Device-age hard floor
    if protected_device_state.age_registration == MINOR:
        if policy_prohibits(candidate.content.content_class):
            return DENY_RENDER("MINOR_REGISTERED_DEVICE")

    # Temporary handover overrides stale adult state
    if protected_device_state.temporary_under18_mode == ACTIVE:
        if candidate_requires_adult_only_authority(candidate):
            return DENY_RENDER("TEMPORARY_UNDER18_MODE")

    # Recipient / eligibility
    if candidate.recipient_context.eligibility_state == NOT_ELIGIBLE:
        deny(RECIPIENT_NOT_ELIGIBLE)

    if candidate.recipient_context.eligibility_state == UNKNOWN:
        deny(ELIGIBILITY_UNKNOWN)

    if candidate.recipient_context.eligibility_state == EXPIRED:
        deny(ELIGIBILITY_EXPIRED)

    if candidate.recipient_context.eligibility_state == REVOKED:
        deny_or_revalidate()

    # Policy
    if candidate.policy_context.parental_control_state == DENY:
        deny(PARENTAL_POLICY_DENY)

    if candidate.policy_context.platform_policy_state == DENY:
        deny(PLATFORM_POLICY_DENY)

    if policy/review state cannot currently authorize:
        deny_or_require_revalidation()

    # Epochs
    require(candidate.policy_context.policy_epoch
            == current_state.policy_epoch)

    require(candidate.policy_context.revocation_epoch
            == current_state.revocation_epoch)

    # Identity / target / path
    require(device_binding_valid(candidate.render_request.device_id))
    require(application_binding_valid(candidate.render_request.application_id))
    require(content_binding_valid(candidate.content.content_digest))
    require(output_targets_permitted(candidate.render_request.output_targets))
    require(sink_binding_valid(candidate.finality_sink))

    # Attestation where required by the assurance profile
    require(device_or_sink_attestation_acceptable_if_required())

    # Adult viewing context where required
    if adult_context_required(candidate):
        require(current_adult_viewing_context_is_valid())

    decision = construct_scoped_policy_decision()

    evidence_ref = commit_protected_validation_evidence(decision, candidate)

    return ALLOW with evidence_ref and narrowly scoped permitted_effects
```

No single check should be treated as sufficient authorization.

# 10. Protected Validation Evidence

A reference implementation should record, at minimum, enough protected information to reconstruct why authority was issued without logging unnecessary personal data.

A useful protected record may include:

```text
evidence_id
candidate_digest
decision_id
validated policy epoch
validated revocation epoch
eligibility result reference
device/application/sink bindings
permitted effect scope
timestamp
authority identifier
authenticator / integrity protection
```

This is an implementation structure, not a new wire schema.

Privacy guidance:

- prefer opaque identifiers over content titles;
- prefer digests over URLs where sufficient;
- do not store biometric templates;
- do not store exact date of birth when an eligibility result is sufficient;
- avoid unnecessary viewing-history logs.

# 11. Authority Issuance Algorithm

```text
function issue_authority(candidate, decision, evidence_ref):

    require(decision is currently ALLOW_RENDER
            or policy-defined ALLOW_RESTRICTED_MODE)

    require(evidence_ref committed)

    authority = {
        authority_id: fresh_unique_id(),
        candidate_act_id: candidate.candidate_act_id,
        candidate_digest: digest(candidate),
        validation_evidence_ref: evidence_ref,
        permitted_effects: decision.permitted_effects,

        content_digest: candidate.content.content_digest,
        recipient_context_id: candidate.recipient_context.recipient_context_id,
        device_id: candidate.render_request.device_id,
        application_id: candidate.render_request.application_id,

        sink_id: candidate.finality_sink.sink_id,
        sink_type: candidate.finality_sink.sink_type,

        policy_epoch: decision.validated_policy_epoch,
        revocation_epoch: decision.validated_revocation_epoch,

        nonce: candidate.freshness.nonce,
        issued_at: now,
        expires_at: bounded_expiry(),

        consumption: select_consumption_profile(),
        max_frame_count: optional_bound,
        max_duration_ms: optional_bound
    }

    authority.signature_or_mac =
        protected_authenticator.protect(authority)

    return authority
```

The expiry of an authority must not exceed the validity of any load-bearing state on which the authorization depends.

# 12. Finality Sink Verification Algorithm

The sink must verify immediately before the protected effect.

```text
function verify_at_sink(candidate, authority, runtime):

    validate_candidate_schema(candidate)
    validate_authority_schema(authority)

    deny_if_missing_or_malformed(authority)

    verify_authenticator(authority)

    require(authority.candidate_act_id == candidate.candidate_act_id)
    require(authority.candidate_digest == digest(candidate))

    require_if_present(authority.content_digest
                       == candidate.content.content_digest)

    require_if_present(authority.recipient_context_id
                       == candidate.recipient_context.recipient_context_id)

    require_if_present(authority.device_id
                       == candidate.render_request.device_id)

    require_if_present(authority.application_id
                       == candidate.render_request.application_id)

    require(authority.sink_id == runtime.sink_id)
    require(authority.sink_id == candidate.finality_sink.sink_id)

    require(authority.policy_epoch == runtime.current_policy_epoch)
    require(authority.revocation_epoch == runtime.current_revocation_epoch)

    require(now >= authority.issued_at)
    require(now < authority.expires_at)

    require(runtime.device_attestation_state
            satisfies active assurance profile)

    require(requested output path is explicitly authorized)
    require(all required permitted_effects are present)

    # Prevent output widening
    DISPLAY authority does not imply CAST
    DISPLAY authority does not imply MIRROR

    # Evaluate capture / external display according to policy
    if runtime.screen_capture_active and policy forbids it:
        deny
    if runtime.external_display_attached and policy requires separate authority:
        deny_or_revalidate

    enforce_consumption_mode(authority, runtime)

    if any required condition is absent / stale / invalid:
        KEEP_NON_RENDERABLE

    otherwise:
        enable only the specifically permitted protected effect
```

The sink must never convert an invalid result into a warning followed by rendering.

# 13. Reference Sink-to-Effect Mapping

The source draft defines sink types and effect types separately. The following mapping is a useful **reference implementation mapping**, not an additional normative protocol rule.

| Sink type | Typical protected effect(s) |
|---|---|
| `CONTENT_KEY_RELEASE` | `RELEASE_CONTENT_KEY` |
| `DECRYPTION_GATE` | `DECRYPT` |
| `MEDIA_DECODER_GATE` | `DECODE` |
| `GPU_COMPOSITOR_GATE` | `CREATE_PROTECTED_SURFACE`, `COMPOSITE`, `DISPLAY` as applicable |
| `PROTECTED_SURFACE_GATE` | `CREATE_PROTECTED_SURFACE` |
| `DISPLAY_ENABLE_GATE` | `DISPLAY` |
| `AUDIO_OUTPUT_GATE` | `PLAY_AUDIO` |
| `CAST_GATE` | `CAST` |
| `MIRROR_GATE` | `MIRROR` |

A deployment may chain multiple sinks.

Example:

```text
KEY RELEASE
   |
   v
DECRYPTION
   |
   v
PROTECTED DECODER
   |
   v
PROTECTED SURFACE
   |
   v
GPU / COMPOSITOR
   |
   v
DISPLAY
```

A chained deployment must define whether one authority covers multiple explicitly listed effects or whether separate sink-bound authorities are required at each protected boundary.

# 14. Dual-Boundary Variation

A deployment MAY use:

1. **Delivery Finality** — whether protected content may be transported to or retained by the device.
2. **Rendering Finality** — whether the protected content may become perceptible.

The critical rule is:

```text
DELIVERED != RENDERABLE
```

A successful delivery decision must not silently create rendering authority.

# 15. Device and Family State Model

The source draft requires a clear separation of five concepts:

1. **Device Age Registration**
2. **Adult Eligibility**
3. **Current Adult Viewing Context**
4. **Temporary Under-18 Handover State**
5. **Rendering Finality Authority**

These must not be collapsed into one Boolean such as `isAdult=true`.

---

# 16. Device Age Registration

## 16.1 Minor-Registered Device

A minor-registered device is a protected hard-deny baseline for adult-only content under the strict child-safety profile.

```text
MINOR-REGISTERED DEVICE
        |
        v
adult-only authority prohibited
        |
        v
CONTENT REMAINS NON-RENDERABLE
```

An adult account login, adult service token, downloaded adult content, cached content, or previous adult session does not override this baseline.

Changing the device itself from minor-registered to adult-registered, where allowed, requires explicit authorized re-provisioning / age-registration procedure.

## 16.2 Adult-Registered Device

Adult registration only permits an attempt to establish adult authorization.

It is **not** permanent display permission.

```text
ADULT-REGISTERED DEVICE
        |
        v
adult verification / protected context
        |
        v
PED validation
        |
        v
bounded authority
        |
        v
Finality Sink
```

---

# 17. Protected Adult Viewing Context

A higher-assurance deployment may establish a protected Adult Viewing Context using, for example:

- secure device PIN;
- passkey;
- local biometric confirmation;
- trusted wearable confirmation; or
- another protected verification mechanism accepted by policy.

The protocol does not require one universal mechanism.

The protected result can express only that the required adult-presence condition is current. It need not expose civil identity, biometric template, or exact age to the content provider.

Possible context bindings include:

- device;
- protected profile;
- application;
- content class;
- session;
- policy epoch;
- revocation epoch;
- sink;
- freshness;
- expiry;
- revalidation condition.

A previous `OVER_18` credential or continued adult login must not, by itself, be treated as current adult presence.

# 19. Temporary Under-18 Handover Mode

This is a first-class protected state transition.

## 19.1 Activation

Before an adult hands the device to a child:

```text
PROTECTED ADULT VIEWING CONTEXT
        |
        v
TEMPORARY UNDER-18 MODE ACTIVATED
        |
        +-- invalidate / suspend / consume /
        |   cryptographically supersede incompatible adult authority
        |
        +-- advance protected policy/security epoch
        |
        +-- prohibit new adult-only authority
        |
        v
TEMPORARY MINOR BASELINE
```

While active, the following must not independently restore adult rendering authority:

- adult account login;
- stored `OVER_18` credential;
- browser cookie;
- application token;
- cached adult session;
- downloaded media;
- previously released application state;
- earlier adult verification.

## 19.2 Timer Expiry

A timer expiry should **not** silently reactivate adult content while the device may still be with the child.

Safer transition:

```text
TEMPORARY UNDER-18 MODE
        |
        | timer expires
        v
UNVERIFIED ADULT STATE
        |
        | no adult rendering authority
        v
PROTECTED ADULT RE-AUTHORIZATION REQUIRED
```

## 19.3 Exit

Leaving the safer state and restoring adult rendering must use a protected adult-authorized transition when required by policy.

Design principle:

> Entering the safer state can be easy; leaving the safer state is protected.

# 20. Handover and Revalidation Events

A current adult lease/context should expire, suspend, or require revalidation when relevant events occur, including:

- device lock or unlock;
- protected user/profile change;
- application termination;
- material backgrounding;
- session expiry;
- inactivity;
- adult-presence freshness expiry;
- content-class escalation;
- rendering sink change;
- output-path change;
- casting start;
- mirroring start;
- remote-display start;
- XR output start;
- security-epoch change;
- device-attestation change;
- policy-epoch change;
- revocation-epoch change;
- another deployment-defined event indicating context loss.

After such an event, old adult status is not sufficient.

# 21. Immediate Handoff While Content Is Already Playing

This is the hardest physical-world variant.

The source draft explicitly does **not** claim that a device can always determine which physical person is currently viewing the screen.

If:

1. an adult authenticates;
2. valid restricted content begins playing;
3. the still-valid, still-unlocked device is immediately handed to a child; and
4. no protected event or signal causes revalidation,

then the device cannot reliably infer the physical handoff.

Higher-assurance deployments should therefore use bounded or event-driven revalidation.

Possible triggers include:

- lease expiry;
- inactivity;
- screen off/on;
- application transition;
- new restricted title;
- content-class escalation;
- output-path change;
- high-risk policy event;
- protected continuity signals.

For higher-risk content, a deployment may:

```text
PAUSE / BLANK / MUTE
        |
        v
REVALIDATE
        |
    +---+---+
    |       |
 VALID    INVALID
    |       |
 RESUME   REMAIN NON-PERCEPTIBLE
```

Continuous camera monitoring or continuous facial recognition is not required by the protocol.

---

# 22. Performance Logic: Protect State Transitions, Not Every Frame

The architecture is not intended to run a full expensive authorization transaction at 60/120 Hz for every frame.

Use bounded leases/epochs.

```text
AUTHENTICATE
    |
VERIFY POLICY
    |
ISSUE FINALITY LEASE
    |
PROTECTED SESSION
    |
RENDER MANY FRAMES
    |
REVALIDATE ON EXPIRY OR SECURITY CHANGE
```

A `FRAME_WINDOW` may bind:

```text
Device
+ Session
+ Content or Policy
+ Sink
+ Expiry
+ Nonce
+ Frame count / duration
```

The source draft gives examples of a 10-minute lease and a 30-minute 120-Hz cloud-gaming session to illustrate that cryptographic checks can protect authorization transitions rather than every individual frame.

These examples are architectural illustrations, not mandatory lease durations.

---

# 23. Content-Key and Decryption Variation

Withholding the usable content key is a strong Finality Sink.

Requirements:

- failed validation must not release the usable key into an unprotected application context;
- a previously released bounded key should remain constrained by protected state such as session, content, policy epoch, time, frame window, or equivalent state.

Possible chain:

```text
ENCRYPTED CONTENT
      |
      v
KEY WITHHELD
      |
 valid authority?
   +--+--+
   |     |
  NO    YES
   |     |
   v     v
WITHHOLD RELEASE INTO PROTECTED PATH
```

---

# 24. Decoder / GPU / Compositor Variation

For content already encrypted locally or decoded in a protected path, the Finality Sink can exist at:

- decoder;
- GPU command submission;
- protected surface;
- compositor;
- display plane.

The implementation must prevent ordinary application code from converting a denied Candidate Act into a visible frame using an alternate unprotected surface.

A strong implementation may keep decoded frames inside protected memory/surfaces until finality authority is verified.

---

# 25. Audio / Cast / Mirror / XR / Secondary Output Variation

Restricting local display alone is incomplete where the same content can escape through:

- speaker;
- headset;
- HDMI / external display;
- wireless cast;
- screen mirroring;
- remote-display API;
- accessibility capture;
- XR compositor;
- other secondary output.

Each protected consequence should be explicitly authorized.

Example:

```text
Authority: DISPLAY
    |
    +--> DISPLAY  -> may be permitted
    +--> CAST     -> NOT implied
    +--> MIRROR   -> NOT implied
```

A sink verifier should inspect runtime output state, including screen-capture and external-display state when those are policy-relevant.

---

# 26. AI-Generated and AI-Transformed Content

AI may generate restricted content that has no stable catalogue ID.

The Candidate Act supports:

- content digest;
- generation model ID;
- classification source;
- protected output state.

Rules:

1. generation does not create authority;
2. transformation does not automatically inherit authority;
3. the final or transformed representation should be bound to the classification and authority used for the attempted rendering;
4. policy may permit low-risk transformations such as resizing to preserve authorization;
5. higher-risk generative modification can require new policy evaluation and new authority.

Conceptually:

```text
RESTRICTED OBJECT
      |
      v
AI TRANSFORMATION
      |
      v
NEW REPRESENTATION
      |
      v
POLICY RE-EVALUATION / AUTHORITY CHECK
      |
      v
FINALITY SINK
```

---

# 27. Replay, Theft, Revocation and Rollback

A Finality Lease must not be a simple unrestricted bearer token.

Bindings can include:

- lease ID;
- device public key;
- session ID;
- content or policy digest;
- sink ID;
- policy epoch;
- revocation epoch;
- expiry;
- nonce;
- permitted effect scope.

Replay defenses may include:

- unique nonces;
- expiry;
- session binding;
- device-key binding;
- sink binding;
- policy epochs;
- revocation epochs;
- atomic consumption;
- current status checks.

The sink should verify current policy and revocation epochs immediately before materialization.

Old authority must not override a later:

- parental-policy change;
- account-state change;
- legal-policy change;
- device revocation;
- recipient-eligibility change.

Rollback-resistant protected state is required where the attacker can restore snapshots or old local state.

---

# 28. Offline and Authorization-Service Outage Logic

The protocol need not require a live online authorization transaction for every frame or object.

A bounded Finality Lease can permit offline operation until expiry.

```text
ONLINE AUTHORIZATION
       |
       v
FINALITY LEASE
       |
       v
BOUNDED OFFLINE OPERATION
       |
       v
EXPIRY
       |
       v
RENEW / REVALIDATE
```

Failure behavior is policy/risk dependent:

- high-risk content may fail closed immediately when current authorization cannot be established;
- lower-risk already-authorized sessions may continue only within a bounded still-valid lease, where policy permits.

Lease duration is policy-defined, not hard-coded by the protocol.

---

# 29. Policy Authority Separation

The execution-finality layer does not define what is child-safe.

Separate:

```text
AGE / ELIGIBILITY PROVIDER
          |
          v
     ELIGIBILITY FACT

POLICY AUTHORITY
          |
          v
   POLICY ID / VERSION

PED / AUTHORIZATION
          |
          v
FINALITY AUTHORITY

FINALITY SINK
          |
          v
PROTECTED EFFECT
```

Credential issuer, policy authority, finality-authority issuer, and hardware control need not be the same entity.

This separation also supports different jurisdictional policies.

---

# 30. Privacy Requirements

Minimize disclosure.

The sink generally needs:

- validated eligibility outcome;
- bindings necessary for effectuation;
- current policy/epoch state;
- device/application/sink state.

It does not necessarily need:

- name;
- exact age;
- date of birth;
- face;
- biometric template;
- detailed browsing history.

Logs should avoid unnecessary:

- content titles;
- URLs;
- civil identity attributes;
- detailed viewing history.

Use:

- opaque IDs;
- digests;
- protected commitments;
- minimal attribute proofs,

where sufficient.

---

# 31. Censorship / Scope-Abuse Safeguards

A mechanism capable of preventing content rendering can be abused if its scope is uncontrolled.

Implementation governance should preserve:

- explicit purpose scope;
- content-class scope;
- eligibility-class scope;
- jurisdiction;
- policy version;
- expiry;
- sink scope;
- policy transparency;
- auditable policy changes;
- separation of powers;
- privacy minimization;
- separation between child-safety policy and general adult content-control policy.

These are architectural safeguards, not a universal policy definition.

---

# 32. Assurance Profiles

The source draft supports progressive assurance.

## 32.1 Software Finality

Typical placement:

```text
Application / Browser / OS service
```

Useful for interoperability and early deployment, but ordinary software compromise may bypass it.

## 32.2 OS / TEE Finality

Typical placement:

```text
Application
   |
   v
Trusted OS / Protected Service / TEE
   |
   v
Protected media path
```

Stronger against compromised applications.

## 32.3 Hardware Rendering Finality

Typical placement:

```text
Protected OS / TEE
      |
      v
Protected media path
      |
      v
GPU / Decoder / Compositor / Display / Audio / XR
```

Stronger where hardware provides a non-bypassable effect boundary.

No profile should claim complete protection against unrestricted physical hardware control.

---

# 33. Staged Deployment

A realistic deployment progression from the source draft is:

1. **Software enforcement** — browsers, apps, OS implement protocol semantics.
2. **Trusted execution** — authorization moves into secure OS / TEE components.
3. **Protected media paths** — restricted content cannot bypass trusted execution path.
4. **Hardware finality** — final gate moves into protected media, GPU, compositor, display, audio, or XR pipeline.
5. **Ecosystem adoption** — content providers, AI providers, browsers, app stores, and platforms use the interoperable interface.

The interface can be standardized while the physical implementation remains platform-specific.

# 37. Fail-Closed Decision Matrix

| Condition | Required protected result |
|---|---|
| Missing authority | Non-renderable |
| Malformed authority | Non-renderable |
| Invalid authenticator | Non-renderable |
| Expired authority | Non-renderable |
| Stale policy epoch | Non-renderable / revalidate |
| Stale revocation epoch | Non-renderable / revalidate |
| Replayed nonce | Non-renderable |
| Consumed single-use authority | Non-renderable |
| Content mismatch | Non-renderable |
| Recipient mismatch | Non-renderable |
| Device mismatch | Non-renderable |
| Application mismatch | Non-renderable |
| Sink mismatch | Non-renderable |
| Output mismatch | Non-renderable |
| Device attestation invalid | Non-renderable where required |
| Device attestation unknown | Fail according to active assurance profile; never silently widen authority |
| Parental policy DENY | Non-renderable |
| Platform policy DENY | Non-renderable |
| Eligibility NOT_ELIGIBLE | Non-renderable |
| Eligibility UNKNOWN | Non-renderable / revalidate |
| Eligibility EXPIRED | Non-renderable / revalidate |
| Eligibility REVOKED | Non-renderable |
| Temporary Under-18 mode active | No new adult-only authority |
| Minor-registered device | No adult-only authority under strict profile |
| Timer for handover mode expires | Do not silently restore adult rendering |
| Cast requested with display-only authority | Non-renderable on cast path |
| Mirror requested with display-only authority | Non-renderable on mirror path |
| New AI-generated restricted representation | Require policy/authority appropriate to final representation |
| Current authorization unavailable for protected high-risk effect | Fail closed |

## 40.1 Canonical candidate encoding

Needed for interoperable `candidate_digest`.

## 40.2 Authority cryptography

Need to select and version:

- signature vs MAC;
- algorithm;
- key identifiers;
- key discovery;
- rotation;
- revocation;
- hardware-backed key policy.

## 40.3 Transport

Could be:

- protected IPC;
- OS service call;
- local enclave channel;
- network API;
- vendor platform API.

## 40.4 Attestation profile

Need to define:

- evidence format;
- trust anchors;
- acceptable measurements;
- freshness;
- device/sink identity binding;

## 40.5 Age / eligibility credential format

These depend on assurance profile and device capabilities.

# 41. Security Claims and Non-Claims

## This architecture does claim

- an upstream age or policy result should not become indefinite rendering authority;
- current authority can be made load-bearing at the protected rendering boundary;
- a minor-device hard baseline can prevent adult authority under the strict profile;
- Temporary Under-18 mode can invalidate/supersede stale adult authority when implemented in protected state;
- output effects can be separately scoped;
- replay/revocation/epoch checks can prevent reuse of stale authority;
- expensive cryptographic checks can be associated with security transitions rather than every frame.

## This architecture does not claim

- perfect identification of the physical person looking at the screen;
- continuous viewer recognition;
- prevention of external-camera recording;
- a universal age-estimation system;
- a universal definition of harmful content;
- immunity when an attacker has unrestricted control of the hardware;
- that an ordinary software-only toggle is hardware-rooted finality;
- that a server-side policy endpoint alone is a Finality Sink.

---

# 42. Five Core Rules

The source draft reduces the architecture to five central rules:

1. **No continuous biometric surveillance.**
2. **No age credential is itself execution authority.**
3. **No valid finality authority means no protected effect.**
4. **No alternate path may bypass the protected effect boundary.**
5. **Cryptographic verification protects authorization transitions, not every frame.**

# 44. Implementation Checklist

Before describing an implementation as enforcing this profile, verify:

- [ ] Candidate Act exists before protected rendering.
- [ ] Candidate remains non-renderable during validation.
- [ ] Strict JSON validation is implemented.
- [ ] Load-bearing candidate digest is deterministic.
- [ ] PED evaluates all predicates required by the selected deployment.
- [ ] Age proof alone cannot trigger rendering.
- [ ] Protected validation evidence is committed.
- [ ] Authority is scoped and cryptographically protected.
- [ ] Authority binds current content/device/recipient/application/policy/revocation/freshness/effect/sink as required.
- [ ] Finality Sink independently verifies.
- [ ] Current epochs are checked at effectuation.
- [ ] Replay state is enforced.
- [ ] Output widening is prevented.
- [ ] Alternate rendering routes are closed for the claimed assurance profile.
- [ ] Minor-device baseline is protected where that profile is implemented.
- [ ] Adult registration alone does not render.
- [ ] Adult Viewing Context is bounded.
- [ ] Temporary Under-18 mode blocks new adult-only authority.
- [ ] Prior adult authority is invalidated/suspended/superseded on handover mode.
- [ ] Timer expiry does not silently restore adult rendering.
- [ ] Protected re-authentication is required to restore adult context where policy requires.
- [ ] Meaningful security transitions trigger expiry/suspension/revalidation.
- [ ] Frame-window limits are enforced.
- [ ] Session-bound authority is not transferable.
- [ ] AI-generated/transformed content cannot acquire authority merely because it was generated.
- [ ] Offline operation remains bounded.
- [ ] Privacy-minimized logging is implemented.
- [ ] Failure is fail-closed.
- [ ] Security claims accurately match the actual enforcement boundary.
